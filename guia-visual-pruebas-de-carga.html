Los escenarios del script

Una prueba de carga es, ante todo, una forma

Antes de hablar de milisegundos hay que decidir cuánta carga, durante cuánto tiempo y con qué curva. Esa forma es la pregunta que se le hace al sistema. Estos son los escenarios que ya trae perf/scripts/register_person_k6.js; se eligen con --env SCENARIO=<nombre>.

Cada figura tiene su propia escala: están dibujadas para comparar formas, no tamaños. Los usuarios virtuales (VUs) van en el eje vertical y el tiempo en el horizontal.

Cerrado o abierto. En el modelo cerrado usted fija cuántos usuarios hay; si el sistema se pone lento, esos usuarios envían menos peticiones, justo cuando habría que enviarle más. En el abierto fija cuántas peticiones llegan por segundo, lleguen o no a atenderse, que es como se comporta el tráfico real. Más abajo se ve la diferencia con datos.

El promedio miente, la cola no

Las 34.776 peticiones de la corrida de la portada, agrupadas por cuánto tardaron. La mayoría se atendió en 16 a 64 ms. Pero a la derecha hay una cola larga, y ahí están las personas con peor suerte: el promedio la esconde y el p95 y el p99 la muestran.

Modelo cerrado · con pool de conexiones

Más usuarios no es más rendimiento: es más espera

Se subió la carga por escalones, de 1 a 800 usuarios virtuales, con dos corridas por escalón. A partir de 10 VUs el throughput deja de crecer y oscila entre 5.100 y 9.400 peticiones por segundo. Lo que sí sigue creciendo es el tiempo: el p95 pasa de 1,6 ms a 202 ms.

No es casualidad, es la ley de Little: usuarios en el sistema = throughput × tiempo por iteración. Con 800 VUs, 7.042 req/s × 0,106 s ≈ 746. Si el throughput no puede crecer, lo único que puede crecer es el tiempo.

Observabilidad

El servidor dice 0,1 ms. El usuario espera 200.

Mismo experimento que el anterior. k6 mide desde afuera, desde que envía la petición hasta que recibe la respuesta. Actuator mide desde adentro, con http.server.requests, y empieza a contar cuando un hilo por fin toma la petición.

Los dos tienen razón. La diferencia es el tiempo que la petición pasó en la red, en el propio cliente y sobre todo esperando en la cola un hilo libre. Si el servidor responde en décimas de milisegundo y el usuario espera cientos, optimizar el código de negocio no sirve: el problema es capacidad.

Modelo abierto

El tráfico real no espera a que el servidor termine

Ahora se fija cuántas peticiones llegan por segundo, y se mide cuántas se atienden. Mientras las dos cifras coinciden, el servicio da abasto; cuando se separan, sobra trabajo, y k6 lo reporta como dropped_iterations: iteraciones que no pudo ni empezar.

Un cuello de botella real, en este repositorio

Un defecto que solo aparece con carga

RegistryRepository abre una conexión nueva en cada operación, y registerVoter hace dos por petición. Con un usuario funciona perfecto: ninguna prueba unitaria ni de integración lo va a detectar.

// registraduria/.../RegistryRepository.java
private Connection getConnection() throws SQLException {
    return DriverManager.getConnection(jdbcUrl, username, password);
}

La conclusión que se busca: una prueba de carga sin observabilidad dice que algo va mal; con observabilidad dice qué arreglar. HikariCP ya viene con Spring Boot: agregarlo, repetir la medición y documentar el antes y el después es una de las actividades del taller.

Resiliencia

Un pico súbito, y la recuperación

Una prueba de pico no pregunta cuánto aguanta el sistema, sino qué pasa cuando la carga cambia de golpe y si vuelve a la normalidad. En esta medición del laboratorio los usuarios subieron de 20 a 400 y volvieron a bajar en dos minutos.

En su máquina

Paso a paso

Los comandos de Maven se ejecutan dentro de registraduria/; los de k6, desde la raíz del repositorio.

  1. Compile y levante el servicio

    cd registraduria
mvn -DskipTests clean package
java -jar target/registraduria-1.0-SNAPSHOT.jar

  2. Compruebe que responde

    Antes de medir nada: si el servicio no está arriba, k6 reporta errores que no son del sistema.

    curl http://localhost:8080/actuator/health
# {"status":"UP", ...}

  3. Mida la línea base

    Vuelva a la raíz. La línea base es la referencia contra la que se compara todo lo demás.

    cd ..
k6 run --env BASE_URL=http://localhost:8080 --env SCENARIO=baseline \
       perf/scripts/register_person_k6.js

  4. Suba a carga esperada

    Rampa hasta 200 VUs, diez minutos sostenidos.

    k6 run --env BASE_URL=http://localhost:8080 --env SCENARIO=load \
       perf/scripts/register_person_k6.js

  5. Verifique el resultado de negocio, no solo el 200

    El segundo script comprueba que bajo carga el servicio siga respondiendo lo correcto. Fíjese en la métrica register_failed.

    k6 run --env BASE_URL=http://localhost:8080 --env SCENARIO=baseline \
       perf/scripts/register_voter_k6.js

  6. Pregúntele al servidor

    Durante una corrida, compare el p95 de k6 con el que mide el propio servicio.

    curl -s "http://localhost:8080/actuator/metrics/http.server.requests" | jq
curl -s "http://localhost:8080/actuator/metrics/jvm.threads.live" | jq

Reinicie el servicio entre corridas. La base de datos H2 vive mientras vive el proceso: si repite una prueba sin reiniciar, los ids ya existen y todo lo que esperaba VALID devuelve DUPLICATED. El umbral se cruza sin que el servicio tenga nada malo. Si no quiere reiniciar, desplace el rango con --env ID_BASE=700000000. Y en Windows, no pase la configuración con set: use --env.

Para el nivel excelente en observabilidad no basta con recoger métricas del servidor: hay que comparar el p95 de k6 con el de http.server.requests y llegar a la causa de la degradación, como en las gráficas de esta página.

Límites de estos datos. Se midió en un portátil, con el servicio fijado a un núcleo, 20 s de calentamiento y dos repeticiones por escalón. Los números sirven para ver la forma de las curvas, no como referencia de capacidad. H2 en memoria abre conexiones mucho más baratas que una base de datos real por red, así que contra PostgreSQL o MySQL la diferencia del pool sería mayor. El p95 del servidor se estima a partir de los intervalos del histograma de Actuator.
